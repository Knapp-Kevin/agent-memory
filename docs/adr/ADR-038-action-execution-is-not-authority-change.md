# ADR-038: Action execution is not authority change

**Status**: Accepted (2026-09-07)
**Program**: Sprint 4c-2 (`docs/plan-sprint4c2-action-authority.md`); research `docs/research-brief-sprint4c2-action-authority-2026-09-07.md` (Entry #52); operator rulings R1-R3, C7, C6, C1 and the iteration-5 rulings of 2026-09-07.

## Context

PRD-001 R1 names **action authority** and **execution evidence** as stages the public API must distinguish. Before this ADR the only implementation of action authority, `procedural_memory.apply_action_governance`, bound a decision the **caller** supplied. At a public boundary that is the assertion shape ADR-037 step 4b-2 removed. PAMA doctrine already carried the authority **dimension** -- the A3/A4/A5 downstream-authority classes and their floors -- and `docs/33` already required "a separate PAMA decision" before an M3 capability gains A4 authority. It lacked the **operation**.

## Decision

1. **`action_execution` is a new PAMA operation**: exercising authority already possessed to cause an externally meaningful action. It joins `pama-decision.schema.json`, the operation table in `docs/04`, the base table in `docs/33` and the reference `_BASE_TABLE` with the minimum rows low `allow_with_ledger`, medium `require_review`, high `require_review`, critical `require_external_verification`.
2. **`authority_change` is not reinterpreted.** It changes the set or degree of authority an actor possesses; `action_execution` exercises authority already possessed. Collapsing them would contaminate audit semantics and future policy reasoning: a later reviewer must be able to answer "who changed this agent's authority?" and "which actions did it perform under that authority?" without reverse-engineering context from one overloaded enum value. `authority_change` stays absent from the table by decision.
3. **`action_execution` is not a memory mutation** merely because its governance decision or its evidence is subsequently recorded in memory. The memory stages (`propose`, `approve`, `commit`) refuse it; it has its own entry points.
4. **Risk-derived action policy and authority-class floors are independent governance constraints.** The effective outcome is the strictest of the operation/risk cell, the authority-class floor and every other applicable floor over the PAMA outcome ordering. A4 lifts any weaker result to at least `require_review`; A5 to `require_external_verification`. High risk stays `require_review` rather than being raised to external verification: critical already establishes that boundary, and A5 independently forces external verification where authority characteristics justify it.
5. **Authority-floor constraints are non-dischargeable within the ordinary action-authorization evidence path.** A decision preserves *why* its outcome exists as a set of active constraints (`risk_cell`, `authority_floor:A4_EXTERNAL_ACTION`, `authority_floor:A5_GOVERNANCE_CHANGE`, `target_floor:...`), derived from the proposal so no discharge can remove them. `require_review` from a cell and `require_review` from the A4 floor are different obligations: R5 qualified evidence may discharge the first; the second remains. Ordinary attestation likewise does not discharge the A5 floor on this path; A5 is resolved by a separate external-verification governance mechanism, not by laundering the same evidence through action authorization. Consequently an executable allow binds only for A0-A3 actions in contract `1.2.0`; A4/A5 actions park with the floor's own requirement. Target-class floors keep the discharge behaviour they have on the memory path.
6. **A bound decision has its ledger, or nothing is bound.** For every bound decision the adapter path builds the canonical PAMA decision document, the receipt naming it and the receipt event **before** exposing the bound decision; any failure fails closed. Executable `allow_with_ledger` implies a resolvable `decision_ref` and a durable receipt. A `decision_ref` pointing at a document that never exists is not provenance.
7. **No `pending` at the execution seam.** `apply_action_governance` keeps its two outcomes, `allow` and `deny`, because they are executable authorization results; PAMA's parked outcomes are governance workflow states and bind nothing. Absence of a bound decision is fail-closed: a host may not execute merely because no denial object exists. An unbound action is **not** the memory path's parked state: no `memory.pending_verification` record is written and the same proposal is not resumable on this path; the route for an A0-A3 action is re-proposal with evidence under fresh identifiers, and A4/A5 have no route in this contract.
8. **A witness requires a bound decision** (allow or deny). It is evidence of what actually happened relative to the governing decision, not merely proof of compliant execution: a deny-bound execution is recorded as a `violation`; an unbound execution report is audit evidence (`action.unbound_execution_reported`), never a governed execution.
9. **A bound execution authorization is single-consumption.** The seam consumes it and the witness is bound to that consumption; a second execution attempt against the same bound decision fails at the seam before host execution. Consumption is keyed on the decision identity (`proposal_id`) and the action identity (`action_id`) and survives supported runtime restart and restoration for state a checkpoint captured; restoration is fail-closed.

## Known limitations

- **Cross-path proposal-id namespace.** Memory commits do not record proposal ids into the action-consumption namespace, so the same identifier may presently appear once in the memory path and once in the action path. Uniqueness is enforced within the governed action path this sprint introduces, not globally across all PAMA operations. Global proposal/action identity coordination remains future work. This is a known namespace limitation, not a security guarantee.
- **Caller-declared classification.** `downstream_authority` and `risk_class` are declared by the caller on the action envelope; nothing yet cross-checks them against the skill (a `SkillArtifact` declares no authority ceiling). The non-discharge mechanism is only as strong as that label.
- **Checkpoint window.** `RestartSafeRuntime` checkpoints after memory commits and deletes; it cannot wrap the memory-layer action module. A host on it must checkpoint after `witness_execution`; the window between consumption and that checkpoint is the host's.

## Consequences

`docs/33` gains the row, the explicit effective rule and the term **active constraint**; `docs/04` gains the row; `policy.Decision` gains `constraints`; `memory/action_authority.py` hosts the action path with the runtime adapter as an injected collaborator (the dependency direction is `memory` -> `runtime`, never the reverse); contract `1.2.0` exposes `authorize` and `witness`. Conformance: `reference/tests/test_policy_action_execution.py`, `test_action_authority.py`, `test_api_action_authority.py`.
