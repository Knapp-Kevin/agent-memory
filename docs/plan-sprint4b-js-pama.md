# Plan: Sprint 4b — the JS runtime evaluates PAMA before it commits, and proves it cell by cell against Python

**change_class**: feature
**doc_tier**: standard
**risk_grade**: L3
**research_artifact**: docs/research-brief-sprint4b-js-pama-2026-09-07.md (ledger Entry #46)
**iteration**: 1 -- **HELD** by the operator on 2026-09-07 after audit attempt 1 (Entry #47, VETO on design grounds): a PAMA evaluation without a discharge route leaves the JS runtime unable to commit any correction, and the storage port's downstream implementer (QOR Agent's Cloudflare Durable Object) would lose its correction path. Deferred to a later research phase that decides between fail-closed-openly and porting a discharge route (transition-rule corpus for review; attestation for critical). No implementation was started; the draft evaluation and its 65-case fixture were verified equal to Python and are kept out of the tree.

**boundaries**:
- limitations: the port covers the base table, floors, modifiers, strictness order and envelope. It does not port discharge (attestations, qualified evidence, verifier registries): a JS `require_review` or `require_external_verification` **parks** -- the correction is refused with the decision attached -- exactly as the Python surface parks without evidence. Recall is unchanged in this cycle; per-candidate `contextual-recall-admission` records are Sprint 4c (brief decision 2).
- non_goals: Sprint 4c; #395 (the Python commit seam's attestation asymmetry); any change to `reference/agentmem_ref/core/policy.py` or its table (`docs/33-pama-decision-table.md` is the doctrine; the Python module is the transcription of record); idempotency and optimistic-concurrency semantics of the JS runtime, which stay as they are.
- exclusions: every Python module except the one new conformance test and the fixture generator it uses; every schema; `schemas/` is not moved.

## Open Questions

None. Brief decision 1 is taken as LD3 (adopt the envelope's field names, so the runtime can honestly declare contract `1.0.0`); decision 2 is deferred to 4c (limitations). Both are stated so the audit can reject them.

**LD6 — After this cycle the JS runtime is fail-closed for corrections, and the plan says so.** Every `correction` cell in the base table is `require_review` (low, medium, high) or `require_external_verification` (critical); an attestation discharges only the latter in Python (`evaluate_with_external_verification`, lines 407-433 of `policy.py`), and the qualified-evidence discharge needs the evaluator-held registry this cycle does not port. So a JS correction parks at every risk class until a later cycle gives the runtime a discharge route (Sprint 4c candidates: the attestation discharge for critical; a transition-rule corpus for review, as the Python side earned in Sprint 2m).
