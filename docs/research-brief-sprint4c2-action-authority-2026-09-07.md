# Research Brief: Sprint 4c-2 — action authority as a PAMA action operation, and execution evidence bound to it

**Date**: 2026-09-07
**Analyst**: The Qor-logic Analyst
**Program**: ADR-035 build-toward, research-led `/qor-enterprise-auto-dev`. Loop 23.
**Implements**: the ideation gate `2026-09-07T1000-d4e5f6/ideation-iter1.json` (the operator accepted the spark record and problem frame and selected the PAMA action operation over an external governance projection, 2026-09-07); Sprint 4c research (Entry #48) section 2, which found action authority caller-supplied
**Scope**: what PAMA doctrine already says about action authority, what the schema and the reference table admit, what `procedural_memory`'s action seam needs from an adapter-produced decision, and what execution evidence needs from that decision

## 1. Doctrine already carries the action-authority dimension; it lacks the operation

PAMA classifies **downstream authority** orthogonally to the operation: `docs/pama/README.md:79-81` defines A3 local workflow mutation, A4 external action ("messages, deployments, purchases, deletions, bookings, or provider state") and A5 governance change. `docs/33-pama-decision-table.md:43` states the rule this sprint implements: "A high-confidence M3 capability promoted successfully under this table does not gain A4 external-action authority unless a **separate PAMA decision** authorizes that authority." The reference already enforces the floors: `git show origin/main:reference/agentmem_ref/core/policy.py | grep -nE '_AUTHORITY_FLOOR = ' -> 115:_AUTHORITY_FLOOR = {A4: REQUIRE_REVIEW, A5: REQUIRE_EXTERNAL_VERIFICATION}`, applied at line 217 of the same file. So the decision that authorizes an action is an ordinary `Proposal` evaluated by `policy.evaluate` (or its evidence and attestation forms), with `downstream_authority` set to the action's class. What doctrine lacks is the **operation** row: the table's operations (`docs/04-governance-and-pama.md:97-109`, `docs/33-pama-decision-table.md:80-94`) are memory mutations; none names "execute this action under an existing procedure".

The schema admits three operations the table deliberately leaves without a base cell: `git show origin/main:schemas/pama-decision.schema.json | grep -nE '"authority_change"' -> 93:            "authority_change",` alongside `capability_promotion` and `other`; `docs/33-pama-decision-table.md:96-102` says they resolve through `_base_outcome`'s `require_review` fallback "for an operation whose risk profile this table has not characterised". Two routes follow: characterise `authority_change` as the action operation, or add an `action_execution` operation to the enum, the table and the doctrine. `authority_change` reads as changing what an agent *may* do (A5 territory); executing an action under authority already held is a different thing, and overloading the word would be the "M5 governance change disguised as M2" pattern that `docs/33-pama-decision-table.md:330` lists as a conformance case, in reverse. **Recommendation: a new `action_execution` operation**, added to `schemas/pama-decision.schema.json`, the operation table in `docs/04-governance-and-pama.md`, the base table in `docs/33-pama-decision-table.md` and `policy._BASE_TABLE`, with the floors doing the authority work: low `allow_with_ledger`, medium `require_review`, high `require_review`, critical `require_external_verification`; any A4 request is lifted to at least `require_review` and any A5 to `require_external_verification` by the existing floors, unchanged. The rows are the plan's to lock; a short ADR should record the operation because it changes a doctrine table.

## 2. The action seam needs an adapter-produced decision, and one more outcome

`git show origin/main:reference/agentmem_ref/memory/procedural_memory.py | grep -nE 'class ActionGovernanceDecision' -> 207:class ActionGovernanceDecision:` carries `decision_ref`, `action_id`, `outcome`, and its `__post_init__` (lines 212-214) admits only `allow` and `deny`. `apply_action_governance` (lines 574-593) binds it, blocking on `deny` and authorising on anything else. An adapter-produced decision maps PAMA outcomes onto this: `allow` and `allow_with_ledger` become `allow`; `block` becomes `deny`; `require_review` and `require_external_verification` are **neither**: the action parks with `enter_pending_verification` among its permitted actions, exactly as `commit_proposal` parks a memory proposal. The seam therefore needs a third outcome (`pending`) or, cleaner, no `ActionGovernanceDecision` at all until a decision permits or denies; the plan chooses. The producer is `GovernedMemoryAdapter.evaluate_proposal` (`reference/agentmem_ref/runtime/adapter.py:178-202`), which already selects three ways through the adapter's own verifier registry, the `approve` stage's path (`reference/agentmem_ref/api/surface.py:46-56`), so there is no new evaluator and no new authority seam: the action decision is a PAMA decision whose `decision_ref` the adapter mints and records as an audit event, and `apply_action_governance` binds *that*. `ActionProposal` (lines 196-203 of `procedural_memory.py`) carries `action_id`, `description`, `skill_version_ref`, `requires_governance` and no PAMA dimension: an action envelope must supply `target_class` (M3 for a procedure), `downstream_authority`, `risk_class`, `reversibility` and `scope`, and `requires_governance=False` cannot be a public input. At the boundary it is the assertion shape, so the surface refuses it (schema `additionalProperties: false`, as the proposal envelope refuses `review_satisfied`).

The only current callers manufacture the decision: `reference/tests/test_procedural_memory.py:137-144` and `reference/run_procedural_memory.py:85`. Both are scaffolding for the seam and become the adapter path's tests.

## 3. Execution evidence: the host observes, the adapter aligns

`record_runtime_execution(action, execution_ref)` (lines 595-601 of `procedural_memory.py`) refuses unless the action is `authorized_not_executed` with a bound decision, then records a bare `execution_ref`. The record form is the witness: `build_execution_witness(composition, *, action_ref, witness_ref, enforcement_mode, delivery_status, enforcement_point_status, action_status, liveness_status, observed_at, ...)` in `reference/agentmem_ref/memory/enforcement_evidence.py:89-110`, whose docstring already states the honest division: "The witness may record a policy violation rather than rejecting the event. Approval satisfaction is only recognized from a separately verified result." `schemas/execution-witness.schema.json` requires `effective_decision` (allow, warn, require_approval, deny), `action_status` (executed, prevented, refused, unknown, not_observed) and `decision_alignment` (consistent, stricter_than_decision, violation, unverifiable), computed by `_alignment` at line 32 of the same module. So the execution-evidence stage takes **observations** from the host (what happened: delivery, action status, liveness) and binds them to the adapter's decision; the host never supplies `effective_decision` or `decision_alignment`. A host that executed a parked action produces a witness with `decision_alignment: violation`, which is evidence of the failure the ideation's problem frame names, recorded rather than laundered. `build_execution_witness` takes a `composition` dict (a decision-composition receipt); the plan must show how the action decision's receipt reaches it, or derive `effective_decision` from the adapter's decision directly.

## 4. Drift found

1. `ActionGovernanceDecision` is two-valued where PAMA is five-valued; the parked state is unrepresentable at the seam (section 2).
2. `ActionProposal.requires_governance` defaults `True` but is caller-settable; `False` is an ungoverned action by assertion. Not reachable from any public surface today; it must stay unreachable.
3. `record_runtime_execution` stores a reference where doctrine wants a witness (Entry #48 section 3 already noted this).

## 5. Recommendation

Plan Sprint 4c-2 as contract `1.2.0` (additive) in three phases. **(1) Doctrine**: an `action_execution` operation in the schema enum, `docs/04-governance-and-pama.md`, `docs/33-pama-decision-table.md` and `_BASE_TABLE`, with a short ADR; the existing thirteen operations' cells and both floors byte-unchanged, pinned by test. **(2) Adapter**: `evaluate_action(action_proposal, *, evidence, attestation)` building the PAMA `Proposal` from the action envelope, evaluating through `evaluate_proposal`, minting `decision_ref`, recording an audit event, and returning either a bound `ActionProposal` (authorised or blocked) or a parked result; `apply_action_governance` keeps its signature and gains no public caller. **(3) Surface**: `authorize(memory, action_envelope, *, evidence=(), attestation=None)` (stage `action_authority`) and `witness(memory, action_ref, observation_envelope)` (stage `execution_evidence`), two new input schemas (`api-action-envelope`, `api-execution-observation`), DoD 20 extended to both, the wheel-install step asserting the new schemas. Adversarial negatives the plan must name: an envelope carrying `requires_governance`, `outcome` or `decision_ref` is refused by schema; an A4 action at low risk still parks; a witness for a parked action records `violation`.
